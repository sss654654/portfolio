매니페스트도 인그레스 규칙도 다 서 있는데 앱 세 종이 뜨지 않았습니다 — **받아 올 이미지가 없었습니다.**
코드는 인터넷의 GitHub에 있고 클러스터는 공유기 뒤 사설 주소라, 이미지를 만들 곳도 그것을 알릴 길도 없었습니다.

## 저장소 둘, 다른 길

|  | cgv-infra | cgv-onprem |
|---|---|---|
| 담긴 것 | 클러스터를 정의하는 매니페스트와 차트 | 앱 소스 셋 — queue-go · booking · frontend |
| 브랜치 | **`main` 하나** | **`dev` 추가** — 기본 브랜치도 dev |
| 그렇게 한 이유 | ArgoCD가 보는 브랜치가 곧 배포된 상태의 정의인데 클러스터가 하나뿐입니다. 환경 구분은 `environments/{dev,stg,prd}` 디렉터리가 이미 하고 있어, 브랜치에 환경 이름을 또 쓰면 같은 것을 두 축이 가리킵니다 | 브랜치가 곧 **이미지 태그를 정하는 축**입니다. `dev-15-17dcc495`의 앞부분이 그것이고, 레지스트리에 올리는 job은 dev에서만 생깁니다 — 리뷰를 거치지 않은 이미지가 배포 후보와 같은 자리에 쌓이지 않습니다 |
| 클러스터가 받는 법 | ArgoCD가 매니페스트를 당겨갑니다 | 노드가 레지스트리에서 이미지를 받아옵니다 |
| 준 자격 | 저장소 읽기 하나 (`read_repository`) | 이미지 읽기 하나 (`read_registry`) |
{:.hl-two}

두 저장소 모두 **직접 push가 막혀 있고 MR로만 들어갑니다.** 설정만 걸어 두지 않고 빈 커밋을 밀어 실제로 거부되는 것을 확인했습니다 — 소유자도 예외가 없습니다. 머지는 스쿼시 뒤 이름표만 옮기는 방식이라 **MR 하나가 커밋 하나**로 남고, 되돌릴 때 그 커밋 하나를 되돌리면 그 작업 전체가 돌아갑니다.

## 길 위에서 정한 것

| 무엇을 | 고른 것 | 그렇게 한 이유 |
|---|---|---|
| Git 서버를 어디에 | 클러스터 밖 — 데스크탑의 도커 | 정본이 자기가 정의하는 대상 안에 살면 대상과 함께 무너집니다. 클러스터를 다시 세울 근거가 클러스터 안에 있으면 안 됩니다 |
| 이미지 이름 | 커밋마다 다르게 — `dev-15-17dcc495` | 이름을 고정하면 매니페스트가 안 변해 배포를 시킬 방법이 없습니다. 파드를 갈려면 파이프라인이 클러스터에 직접 명령해야 하고, 그러면 클러스터 자격이 밖으로 나갑니다 |
| 노드가 쓸 자격 | 프로젝트 전용 토큰, 이미지 읽기 하나 | 내 계정 토큰은 내가 닿는 모든 프로젝트에 통합니다. 노드에 필요한 것은 그 프로젝트의 이미지를 받는 권한뿐입니다 |
| 태그를 누가 되쓰나 | 클러스터 안에서 도는 도구 | 파이프라인이 고치면 배포 정의 저장소에 대한 쓰기 자격이 클러스터 밖으로 나갑니다. 안에서 도는 쪽이 쓰면 밖으로 나가는 자격이 늘지 않습니다 |
{:.hl-dec}

## 통과한 것만 이미지가 된다

검사가 실패해도 이미지가 올라가면 그 검사는 로그일 뿐이고, 로그는 다음 주면 아무도 열지 않습니다. 그래서 실패가 다음 단계를 막게 두는데, **막으려면 고칠 수 있어야 합니다.**

- 자격이 커밋에 섞였는지, 코드에 정적 결함이 있는지, 선언한 의존성이 낡았는지 — 전부 내가 고칠 수 있으므로 **조건 없이 막습니다**
- 이미지 안 OS 패키지의 취약점은 **수정판이 나온 것만** 막습니다. 베이스 이미지를 훑으면 아직 패치가 없는 것이 수십 개 나오는데, 손쓸 수 없는 것으로 막으면 파이프라인이 영구히 빨간불이 되고 결국 게이트를 끄게 됩니다

이 검사를 처음 켠 판에서 **72건**이 나왔습니다. 서비스마다 원인이 달랐습니다.

```
queue-go    2건    직접 import 한 적 없는 간접 의존 — 다른 라이브러리가 딸고 들어왔다
booking    37건    부모 POM 하나가 수백 개 라이브러리의 버전을 정하는데, 그 부모가 낡았다
frontend   33건    베이스 이미지가 업스트림이 더 굽지 않는 태그였다 — 새로 받아도 같은 것이 온다
```

셋 다 **고정해 둔 것이 시간이 지나 낡은 것**입니다. 코드가 안 바뀌었으니 아무 신호가 없었고, 스캔이 처음으로 그 시간을 드러냈습니다. 지금은 0건입니다.

## 막힌 자리

| 증상 | 원인 | 조치 |
|---|---|---|
| 데스크탑에서 하루 열 번씩 뭔가가 죽었다 — GitLab·브라우저·편집기가 번갈아 | Windows가 약속할 수 있는 메모리 총량이 **17.9GB**에 묶여 있었다. 예전에 디스크를 비우려고 페이지파일을 2GB로 고정해 둔 설정이 남아 있었던 것 — **물리 메모리가 6.6GB 남아 있어도 새 요청이 거절된다** | 페이지파일을 12GB로. 총량 28GB. 램은 그대로 두고 크래시가 멎었다 |
| 이미지 스캔 job 둘이 잠금 대기로 죽었다 | 스캐너가 취약점 DB를 지키려고 캐시 디렉터리에 잠금을 건다. 세 job이 한 캐시를 공유하고 있었는데 같은 판에 동시 실행 수를 2로 올렸다 — **동시성이 숨어 있던 공유 자원을 드러냈다** | job 이름별로 캐시 폴더를 갈랐다. 대가는 DB가 여러 벌이 되는 디스크 |
| 의존성 검사가 `429 Too Many Requests` | 검사 대상에 Java 쪽이 들어 있어 라이브러리 버전을 공용 저장소에 물어야 했는데, 같은 공인 주소에서 빌드가 판마다 의존성 수백 개를 받고 있었다. 서버 눈에는 전부 한 명이다 | 원격 조회 없이 판정되는 쪽으로 대상을 좁혔다. Java 쪽은 만들어진 이미지를 여는 검사가 대신 본다 |
{:.hl-tbl}

## 결과

코드를 고쳐 머지한 다음부터는 사람 손이 없습니다.

- 파이프라인이 **검증 5단**을 돌고, 통과한 것만 이미지가 되어 레지스트리에 섭니다
- 클러스터 안 도구가 그 새 이름을 **배포 정의에 커밋으로 되씁니다** — 작성자가 봇으로 찍혀 사람과 갈립니다
- ArgoCD가 그 커밋을 읽어 파드를 교체하고, 노드는 자기 몫 자격으로 이미지를 받아옵니다
- **지금 무엇이 도는지가 git에 적혀 있습니다.** 되돌리는 것은 이전 태그로 되돌리는 커밋 하나입니다
- 파이프라인이 캐시가 채워진 판에서 **1분 54초**입니다 — 처음 다섯 단으로 재편했을 때가 10분 15초였습니다
- 클러스터 밖 어디에도 **클러스터를 조작할 자격이 없습니다**

## 남은 것

**테스트 칸이 비어 있습니다.** 자리는 선언해 뒀지만 도는 job이 없습니다 — 저장소에 돌릴 테스트가 0개입니다. 코드만 읽고 쓰면 통과만 하는 테스트가 되기 쉬워, 앱을 띄우고 동작을 보면서 쓰기로 미뤘습니다. 그래서 지금 이 파이프라인이 보장하는 것은 빌드와 보안 검사까지고, 합쳐진 결과가 실제로 도는지는 아닙니다.

**러너가 데스크탑의 도커 소켓을 물고 있습니다.** 그 소켓으로는 빌드만이 아니라 그 데몬이 할 수 있는 전부를 부를 수 있어, 소켓을 쥔 쪽은 사실상 그 기계의 관리자입니다. 격리된 방식은 빌드마다 데몬을 새로 띄우느라 메모리가 더 들고 캐시도 매번 사라져, 지금 조건에서는 이 상태를 받아들였습니다.
