기준 사례 — 2024년 한국시리즈 극장 생중계 예매, 대기 16만 명.
SLO 5개를 테스트 전 확정, 로비 → 줄서기 → 예매 사용자 여정을 k6로 재현.
회차마다 **먼저 막힌 곳**을 찾아 구조를 바꾸며 dev 1만 → stg 5만 명까지 통과.
{:.lead}

## SLO — 테스트 전 확정

| 관문 | 좋은 사건 | 목표 |
|---|---|---|
| 1 로비 — 사이트 응답 | 2xx (분모 2xx + 5xx) | **99.9%** |
| 2 줄서기 — 대기열 진입 | `enter` 200 · 202 (400 제외) | **99.9%** |
| 3 순번 조회 — 대기 화면 갱신 | `position` 200, 1초 이내 | **99%** |
| 4 전파 — 입장 후 예매 가능 | 입장이 booking에 1초 이내 도달 | **99.9%** |
| 5 예매 여정 — 예매 완료 | 회차 · 좌석 · 선점 · 확정 2xx, 1초 이내 (409 제외) | **99%** |
{:.hl-res}

- **불변식** — 정원 초과 0 · 미소비 잔량 0 · 5xx 0 · 입장 후 403 0, 하나라도 어기면 그 회차는 무효
- **판정** — 서버 지표(Mimir) 기준, 창은 오픈 −60초부터 +5분 · 회차마다 좌석 4,000 · 대기 0에서 시작

## 병목이 옮겨 간 순서

| 회차 · 증상 | 원인 | 조치 → 결과 |
|---|---|---|
| **dev 3만** — k3s 재시작 | 계산이 지목한 Redis는 44% · Traefik 연결 458 → **22,866** → 노드 여유 메모리 1.1GB → etcd 쓰기 **4초** | 노드 8GB × 3 한계 — stg(EKS)로 이전 |
| **stg 8회 · 1만** — 오픈 순간 전파 최대 **4.59초** | 신규 booking JVM 컴파일이 오픈 구간 CPU 117초 점유 · 경합 시 같은 노드 Kafka 브로커 몫 7% | **booking 전용 노드그룹** · 브로커 Guaranteed → **0.251초** |
| **10회 · 2.5만** — 줄서기 **60.912%** | 노드 4 → 3 축소로 queue 파드 2대가 한 노드 — CPU 스케줄 대기, Redis는 여유 | 노드 4 = 파드 4 · 분산 강제 → **100.000%** |
| **13회 · 3만** — k6 `connection reset` 다발 | 발생기 1대 pps 한도 — 초과 패킷을 오류 없이 폐기, 서버는 여유 | 발생기 4대 × 12,500명 |
| **19회 · 5만** — SLO 통과, `enter` 1–2.5초 **13,641건** | queue 파드 4대 중 2대에 연결 **27배** 집중 → Redis 풀 대기 | **미해결** — ALB 연결 되먹임 가설, dev 3만과 같은 유형 |
{:.hl-tbl}

## 10만 명으로 가려면

- **병목 축은 파드당 동시 요청 수** — 사전 계산은 두 환경 모두 Redis를 지목, 실측은 두 번 모두 동시 연결이 먼저 한계 → 조정 대상은 파드 수 · 파드당 동시 요청 상한
- **계산** — 정원 1,000 · 승격 초당 100이면 10만 명 전원 입장 약 16분, 좌석 4,000은 약 80초에 소진 — 약 9만 6천 명은 성능이 아닌 제품 정책의 영역

## 한계

- **실측 상한 5만** — 10만은 발생기 vCPU(계정 한도 64)에 막혀 미측정, 이후는 계수 기반 계산
- **1초 이내 비율 기준이면 5만 줄서기 73.096%** — SLO는 성공률 기준으로 통과
- **soak 테스트 없음** — 모두 12–15분 실행, 메모리 · 커넥션 누수 미확인
