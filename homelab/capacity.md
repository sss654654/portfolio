기준 사례 — 2024년 한국시리즈 극장 생중계 예매, 대기 인원 16만 명.
정원 · 커넥션 풀 · 메모리 상한은 측정 전 설정값 — **dev(홈랩) 1만 명 · stg(EKS) 5만 명까지 실측**.
{:.lead}

## SLO — 테스트 전 확정

| 관문 | 좋은 사건 | 유효한 사건 | 목표 |
|---|---|---|---|
| 1 로비 — 사이트 응답 | 2xx | 2xx + 5xx | **99.9%** |
| 2 줄서기 — 대기열 진입 | `enter` 200(즉시 입장) · 202(대기 등록) | `enter` 전체 − 400 | **99.9%** |
| 3 순번 조회 — 대기 화면 갱신 | `position` 200, 1초 이내 | `position` 전체 | **99%** |
| 4 전파 — 입장 후 예매 가능 | 입장이 booking에 1초 이내 도달 | 입장 확정 전체 | **99.9%** |
| 5 예매 여정 — 예매 완료 | 회차 · 좌석 · 선점 · 확정 2xx, 1초 이내 | 4개 전체 − 409 | **99%** |
{:.hl-res}

- **불변식** — 정원 초과 0 · 미소비 잔량 0 · 5xx 0 · 입장 후 403 0. 에러 버짓 없음, 위반 시 회차 무효
- **분모 제외** — 400(클라이언트 오류) · 409(좌석 소진). 409 포함 시 좌석 4,000 · 16만 명 기준 성공률 2.5%로 왜곡
- **줄서기는 성공률 기준** — 오픈 시 지연보다 실패를 우선 차단, 지연된 `enter`는 재시도로 해결. 1초 이내 비율은 참고값으로 병기
- **전파를 관문으로 둔 이유** — queue의 입장 표시와 booking의 인지 사이에 회차를 요청하면 403. 요청 지표에 실패로 드러나지 않는 구간
- **dev 기준에서 바꾼 3가지** — p99 임계 → **비율**(버킷 증분, 보간 없음) · 참/거짓 조건 → **불변식** · 전파 → 관문

## dev — 홈랩 1만 명

- **한도** — 노드(8GB × 3)가 파드 스펙, 발생기 자리가 인원 상한 결정. 격리망 21회 · 공개 경로 13회 실행
- **1만 — 확정 스펙으로 통과** — 정원 1,000 · 승격 25명/0.5초 · queue 4대 · 1코어 · Redis 풀 50 · booking 2코어 · 1,536Mi · DB 풀 30 · Traefik 3대 · 2Gi → **759,813 요청 · 5xx 0 · 10,000명 전원 완주** · 확정 초당 15.58건 · 매진 440초
- **3만 — 같은 스펙에서 노드가 먼저 한계** — 사전 계산이 지목한 Redis(26,000명에서 포화)는 44%로 여유. 엣지 → Traefik 연결 458 → **22,866** · Traefik 메모리 limit의 90% · 노드 여유 2.3GB → 1.1GB · etcd 디스크 쓰기 0.06초 → **4초** · k3s 재시작
- **stg로 이전** — 노드 8GB × 3 물리 제약, 3만 이상은 EKS(stg)에서 측정

## stg 스펙 — 부하 테스트로 결정

| 항목 | 값 | 결정 회차 · 근거 |
|---|---|---|
| 노드 | m5.xlarge ×7 — **app 4 · booking 2(AZ별 · taint) · 관측 1(AZ 고정)** | 10회(queue 2대가 한 노드) · 8회(JIT 컴파일이 노드 점유) · 노드 교체 시 볼륨 AZ 고정 |
| queue | 4대 고정 · limit **4000m / 2Gi** · Redis 풀 **100** · 기동 시 풀 채움 · 노드 분산 강제 | 6 · 7회(콜드스타트 · GOMAXPROCS) · 10회 · 15회 |
| queue 정원 · 승격 | **1,000** · 50명/0.5초 | dev 확정값 · 5회(승격 상한과 실측 회전이 겹쳐 상한 제거) |
| booking | **2대** · limit **4000m / 3Gi** · 전용 노드 · fetch 8KB/100ms · 오프셋 비동기 커밋 · DB 풀 20 × 2 | 4회(배치 9건 → 20건) · 8회(노드 단독 사용) · Flyway로 2대 |
| Kafka | 브로커 3 · AZ별 1대 · **Guaranteed 1코어** · 파티션 8 · `acks=all` | 8회(공유 노드 경합 시 브로커 몫 7%) |
| 로그 · 관측 | 성공 폴링 접근 로그 제외 · queue 스크레이프 **5초** · Tempo · Loki 한도 상향 | 11회(수집기가 노드 점유) · 16회(피크 표본 1개) · 10회(스로틀) |
| 데이터 | RDS db.m5.large Multi-AZ · ElastiCache cache.m5.large 주 + 복제본 | 사전 계산 — Redis 단일 스레드 1코어가 상한 · MySQL 실측 0.5코어 > t3.small(0.4) |
| 발생기 | c5.2xlarge **× 4** · 대당 12,500명 | 13회(1대 pps 한도 133,432) |
{:.hl-dec}

## 도구

- **k6** — VU 1개 = 사용자 1명의 여정: 로비 폴링 → 오픈 시 `enter` → 순번 폴링 → 입장 → 회차 → 좌석 → 선점 → 확정. 오픈 시각은 전 발생기 동일
- **발생기** — EC2 c5.2xlarge × 4, 대당 12,500명. 1대가 133,432 pps에서 인스턴스 한도 도달, 패킷을 **오류 없이 폐기**(3만 명 회차) → 대수로 확장
- **판정** — 서버 지표(Mimir) 기준, k6는 참고. 창은 오픈 −60초부터 +5분, 분위수 대신 버킷 증분, 회차마다 좌석 4,000 · 대기 0 초기화

## 10만 명 조건

- **병목 축: 파드당 동시 요청 수** — CPU · 풀 크기 · 노드가 아님. 사전 계산은 두 환경에서 Redis를 지목했으나 두 번 모두 동시 연결이 먼저 한계
- **조정 대상 2가지** — 파드 수(파드당 도착 분산) · 파드당 동시 요청 상한(풀 확대는 대기 위치를 Redis 앞으로 옮길 뿐). 즉시 거절은 줄서기 SLO 위반 → 큐 길이 상한 + 짧은 대기로 설계
- **선행 확인** — 되먹임 가설(ALB 로그) · 순번 조회 99.501%(여유 0.5%p, 10만에서 우선 위반 가능) · 발생기 8대 64 vCPU + 클러스터 28 = 92 > 계정 한도 64
- **미해결** — 파드 2대 연결 집중 원인 · 15회 조치 효과 · 신규 booking 파드 컴파일 부하(격리만) · queue `GOMEMLIMIT` 800MiB 대 limit 2Gi 불일치
- **계산상 결과** — 정원 1,000 · 승격 초당 100 기준 10만 명 전원 입장 약 16분, 좌석 4,000은 약 80초에 소진 → 약 9만 6천 명이 잔여 좌석 없이 대기. 성능이 아닌 제품 정책 영역

## 한계

- **실측 상한 5만** — 이후는 계수 기반 계산. 대기열은 사용자 수, 예매는 정원 1,000에 비례. 계수가 2.5만–5만 구간에서 한 번 변해 계산은 근거일 뿐 증명 아님
- **10만 미측정** — 서비스가 아닌 발생기 한계, 계정 vCPU 한도 증설 필요
- **1초 이내 비율 기준이면 5만 줄서기 73.096%로 미달** — 통과 기준은 성공률, 두 값 병기
- **soak 테스트 없음** — 모두 12–15분 실행, 메모리 · 커넥션 누수 미확인
- **운영 기간 하루** — 구축 · 측정 경험
