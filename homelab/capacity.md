2024년 한국시리즈 극장 생중계 예매에서 대기 인원이 16만 명까지 불어났습니다 — 이 시스템은 몇 명까지 받나.
파드에 적어 둔 정원 · 커넥션 풀 · 메모리 상한은 재 보지 않은 값이었습니다.
**dev(홈랩)에서 1만 명까지 재고 물리 한계를 확인한 뒤, stg(EKS)에서 5만 명까지 쟀습니다.**
{:.lead}

## SLO — 인원을 넣기 전에 고정한 것

| 관문 | 좋은 사건 | 유효한 사건 | 목표 |
|---|---|---|---|
| 1 로비 — 사이트가 뜬다 | 2xx | 2xx + 5xx | **99.9%** |
| 2 줄서기 — 누르면 줄에 선다 | `enter` 200(즉시 입장) · 202(대기 등록) | `enter` 전체 − 400 | **99.9%** |
| 3 순번 조회 — 대기 화면이 산다 | `position` 200을 1초 안에 | `position` 전체 | **99%** |
| 4 전파 — 들어가면 문이 열려 있다 | 입장이 booking에 1초 안에 도달 | 입장 확정 전체 | **99.9%** |
| 5 예매 여정 — 표가 손에 들어온다 | 회차·좌석·선점·확정 2xx를 1초 안에 | 넷 전체 − 409 | **99%** |
{:.hl-res}

- **불변식** — 정원 초과 0 · 미소비 잔량 0 · 5xx 0 · 입장 뒤 403 0. 에러 버짓이 없고, 0이 아니면 그 회차 자체가 무효입니다
- **분모에서 뺀 것** — 400은 클라이언트 잘못, 409는 좌석이 실제로 없어서 실패한 것입니다. 409를 넣으면 좌석 4,000에 16만 명이 올 때 성공률이 2.5%로 나옵니다 — 시스템은 같은데 숫자만 40배 다릅니다
- **줄서기는 성공률입니다** — 오픈 순간 느린 것보다 실패하는 것이 훨씬 나쁘고, 느린 `enter`는 한 번 더 누르면 됩니다. 1초 이내 비율은 참고로 같이 적습니다
- **전파를 관문으로 둔 이유** — queue가 "입장했습니다"를 띄운 순간과 booking이 그 사실을 아는 순간이 다르고, 그 사이에 회차를 누르면 403입니다. 이 구간은 어느 요청 지표에도 실패로 안 나타납니다
- dev의 기준은 p99 임계 여섯이었고 stg에서 셋을 바꿨습니다 — 분위수를 **비율**(버킷 증분, 보간 없음)로 · 참/거짓 조건을 **불변식**으로 · 전파를 관문으로

## dev — 홈랩에서 1만 명까지

- **한도가 먼저 있습니다** — 노드(8GB × 3)가 파드 스펙을, 발생기 자리가 인원 상한을 정합니다. 격리망 안에서 21회, 공개 경로에서 13회 돌렸습니다
- **확정한 값** — 정원 1,000 · 승격 25명/0.5초 · queue 4대 · 1코어 · Redis 풀 50 · booking 2코어 · 1,536Mi · DB 풀 30 · Traefik 3대 · 2Gi
- **1만 결과** — 759,813 요청 · 5xx 0 · 10,000명 전원 완주 · 확정 초당 15.58건 · 매진 440초

| 증상 | 원인 | 조치 |
|---|---|---|
| 오픈 순간 booking 경로가 SLO 밖 — `/api/screenings` **4.80초** | **코드가 컴파일되기 전에 부하 도착** — booking이 93분 유휴라 컴파일된 코드가 없는 상태에서 1만 명이 오자 JIT 컴파일러가 CPU **111초** 점유 | 측정 절차에 웜업 → **0.94초**. 같은 성질이 stg에서 노드를 채우는 모양으로 재현(아래 8회) |
| 웜업 뒤 queue 경로가 SLO 밖 — `position` **4.05초** · `enter` **2.49초** | **queue의 Redis 커넥션 풀이 파드당 10** — 오픈에 동시 요청이 파드당 540, 연결 10개를 기다림. 대기 24,158건 · 10,952초 | 풀 **50** → 대기 785초 · 셋 다 1초 아래. 같은 자리(파드당 동시 요청)가 stg 5만 명에서 다시 축 |

**3만 — 왜 stg로 갔나.** 3만을 넣자 계산이 지목한 Redis(26,000명에서 포화)는 **44%**로 여유였고, 먼저 막힌 것은 연결이었습니다 — 엣지 → Traefik 연결이 1만의 458에서 **22,866**으로 늘어 Traefik 메모리가 limit의 90%에 닿고, 노드 여유가 2.3GB → 1.1GB로 줄자 etcd 디스크 쓰기가 0.06초 → **4초**가 되며 k3s가 재시작했습니다. 노드가 8GB 셋뿐인 물리 제약이라, 그 위는 stg에서 잽니다.

## stg 스펙 — 부하 테스트가 정한 값

| 항목 | 값 | 정한 회차 · 근거 |
|---|---|---|
| 노드 | m5.xlarge ×7 — **app 4 · booking 2(AZ별 · taint) · 관측 1(AZ 고정)** | 10회(queue 둘이 한 노드) · 8회(JIT 컴파일이 노드를 채움) · 노드 교체 때 볼륨이 AZ에 묶임 |
| queue | 4대 고정 · limit **4000m / 2Gi** · Redis 풀 **100** · 기동 때 풀 채움 · 노드 분산 강제 | 6 · 7회(콜드스타트 · GOMAXPROCS) · 10회 · 15회 |
| queue 정원 · 승격 | **1,000** · 50명/0.5초 | dev 확정 · 5회(승격 상한과 실측 회전이 겹쳐 상한을 걷어냄) |
| booking | **2대** · limit **4000m / 3Gi** · 전용 노드 · fetch 8KB/100ms · 오프셋 비동기 커밋 · DB 풀 20 × 2 | 4회(배치 9건 → 20건) · 8회(노드를 혼자 씀) · Flyway로 두 대 |
| Kafka | 브로커 3 · AZ마다 하나 · **Guaranteed 1코어** · 파티션 8 · `acks=all` | 8회(공유 노드에서 경합 시 브로커 몫 7%) |
| 로그 · 관측 | 성공한 폴링 접근 로그 제외 · queue 스크레이프 **5초** · Tempo · Loki 한도 상향 | 11회(수집기가 노드를 채움) · 16회(피크 표본 하나) · 10회(스로틀) |
| 데이터 | RDS db.m5.large Multi-AZ · ElastiCache cache.m5.large 주 + 복제본 | 켜기 전 계산 — Redis 단일 스레드 1코어가 상한 · MySQL 실측 0.5코어가 t3.small(0.4) 초과 |
| 발생기 | c5.2xlarge **× 4** · 대당 12,500명 | 13회(한 대의 pps 한도 133,432) |
{:.hl-dec}

## 도구

- **k6** — VU 하나가 한 사람의 여정을 한 번 돕니다: 로비 폴링 → 오픈 순간 `enter` → 순번 폴링 → 입장 → 회차 → 좌석 → 선점 → 확정. 오픈 시각 하나를 발생기 전부가 같게 받습니다
- **발생기** — EC2 c5.2xlarge × 4, 대당 12,500명. 한 대는 133,432 pps에서 인스턴스 한도에 닿아 패킷을 **오류 없이** 버렸습니다(3만 명 회차) — 박스를 키우지 않고 대수로 늘렸습니다
- **판정** — 서버 지표(Mimir)가 정본이고 k6 값은 참고입니다. 창은 오픈 −60초에서 +5분, 분위수 대신 버킷 증분, 회차마다 좌석 4,000 · 대기 0 리셋을 절차로 고정했습니다

## 트러블슈팅 — stg

| 증상 | 원인 | 조치 |
|---|---|---|
| **8회 · 1만** — 같은 인원인데 회차마다 입장 전파가 38ms ↔ **4.59초** · 입장 뒤 403 재시도 1,890건 | **새로 기동한 booking JVM의 컴파일이 오픈 창에 CPU 117초** — 노드 3.6/4 · 런큐 대기 15.2초/초 · 같은 노드의 Kafka 브로커 몫이 7%로 줄어 발행 p99 3.6초. 예열된 파드 둘을 한 노드에 두고 다시 돌려도 90.3% | **booking 전용 노드그룹**(AZ별 한 대 · taint) + **브로커 Guaranteed** → 전파 최대 0.251초 · 403 **0**. 새 파드의 컴파일 부하은 격리만 — 해소는 아님 |
| **10회 · 2.5만** — 줄서기 **60.912%**. Redis는 놀고 파드 넷의 CPU 사용량은 같음 | vCPU 한도를 맞추려 app 노드를 4 → 3으로 줄여 **queue 둘이 한 노드** — limit 합 6.45코어 대 allocatable 3.92 · 런큐 대기 4.16초/초. 느린 것은 Redis가 아니라 응답이 왔을 때 CPU 차례를 못 받은 것 | 노드 수 = 파드 수(4) · 분산 `DoNotSchedule` → **100.000%** |
| **11회 · 2.5만** — 줄서기를 고치니 전파가 **97.445%** | 요청의 96%가 폴링이고 줄마다 접근 로그 — Loki 초당 4,256줄 · 수집기가 노드마다 0.5코어 · booking 노드 런큐 3.30 — **관측이 만든 부하** | 성공한 폴링 로그 제외 · 로그 버퍼링 → **100.000%** · 741줄/초 · 런큐 0.26 |
| **13회 · 3만** — k6에서 `connection reset by peer` 폭주. 서버는 booking CPU 0.52코어 · 5xx 0으로 한가 | **발생기 한 대의 pps 한도** — `pps_allowance_exceeded`가 오르고 있었고, AWS는 넘친 패킷을 오류 없이 버립니다. 서비스가 아니라 도구의 한계 | 대수로 — 4대 × 12,500. 한 대가 조용히 기동하지 않은 회차를 가르는 확인(대별 VU 수)을 실행 절차에 넣음 |

## 10만으로 가려면

- **막히는 축은 파드당 동시 요청 수입니다** — CPU도 풀 크기도 노드도 아닙니다. 켜기 전 계산은 두 환경에서 두 번 Redis를 지목했고, 두 번 다 먼저 막힌 것은 동시에 열린 연결이었습니다
- **조정할 것 둘** — 파드 수(파드당 도착 수를 나눔) · 파드당 동시 요청 상한(풀을 키우는 것은 답이 아님 — 줄이 풀에서 Redis 앞으로 옮겨갈 뿐). 즉시 거절이면 줄서기 SLO가 깨지므로 큐 길이 상한 + 짧은 대기로 설계해야 합니다
- **먼저 확인할 것** — 되먹임 가설(ALB 로그) · 순번 조회가 99.501%로 여유 0.5%p라 10만에서 이 관문이 먼저 깨짐 · 발생기 8대 = 64 vCPU + 클러스터 28 = 92 > 계정 한도 64
- **미해결로 남긴 것** — 파드 둘에만 연결이 몰리는 이유 · 15회 조치의 효과 · 새 booking 파드의 컴파일 부하(격리만) · queue `GOMEMLIMIT` 800MiB 대 limit 2Gi 불일치
- **계산으로 보이는 것** — 정원 1,000 · 승격 초당 100이면 10만 명 전원 입장에 약 16분, 좌석 4,000은 약 80초에 소진 → 약 9만 6천 명이 없는 좌석을 향해 줄을 섭니다. 이것은 성능이 아니라 제품 결정입니다

## 한계

- **실측은 5만까지입니다** — 그 위는 계수로 계산합니다. 대기열은 사용자 수에 비례하고 예매는 정원 1,000에 묶여, 16만이 와도 booking이 상대하는 사람은 1,000명입니다. 다만 계수가 2.5만과 5만 사이에서 한 번 꺾였으므로 계산은 근거이지 증명이 아닙니다
- **10만은 재지 못했습니다** — 서비스 한계가 아니라 발생기 한계입니다. 계정 vCPU 한도 증설이 선행 조건입니다
- **줄서기를 1초 이내 비율로 판정했다면 5만은 73.096%로 미달입니다** — 통과한 것은 성공률 정의이고, 둘을 같이 적습니다
- **soak(장시간 테스트)을 한 번도 안 했습니다** — 전부 12–15분 실행이라 메모리 · 커넥션 누수를 못 봤습니다
- **운영 기간은 하루입니다** — "운영했다"가 아니라 "구축하고 측정했다"입니다
