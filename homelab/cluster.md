물리 서버는 노트북 한 대인데, k3s를 HA로 세우려면 노드가 최소 3대입니다.
etcd가 과반으로 결정을 내리기 때문에 홀수로 최소 3이고, 물리 1대에서 3대를 만드는 방법이 하이퍼바이저였습니다.

## 하이퍼바이저를 무엇으로

호스트 OS 위에 얹는 방식(Type 2)은 먼저 탈락했습니다. 노트북을 상시 가동 서버로 쓸 것이라,
Windows가 자원을 상시 차지하는 것보다 **Windows 업데이트와 재부팅에 VM 3대가 함께 내려가는 것**이 문제였습니다.
하드웨어를 직접 잡는 Type 1 안에서 후보를 추렸습니다.

| 후보 | 판정 |
|---|---|
| ESXi | 무료판은 vCenter가 막혀 Terraform 자동화가 안 되고, 이 노트북 NIC를 잡지 못함 |
| 순수 KVM | 엔진만 있고 VM을 관리할 도구가 없음 — Proxmox가 이 KVM에 관리층을 얹은 것 |
| Hyper-V | 같은 Type 1. 디스크를 따로 잡거나 부팅을 전환할 필요가 없어 **편의는 이쪽이 위** |
| **Proxmox VE** | Debian + KVM · 웹 UI · REST API. 리눅스를 그대로 만질 수 있음 |

Hyper-V가 편의에서 앞선다는 것을 확인하고도 Proxmox를 골랐습니다.
성능이나 기능이 더 나아서가 아니라, **이 홈랩의 목적이 리눅스와 온프레미스를 직접 다루는 것**이었기 때문입니다.
Hyper-V의 강점인 Windows 워크로드 최적화와 Azure 연계는 여기서 쓸 일이 없습니다.

대가는 디스크입니다. Type 1은 설치 시 디스크를 차지해 내장 Windows와 공존이 어렵습니다.
그래서 **외장 USB SSD에 Proxmox를 설치하고 노트북을 그 디스크로 부팅**합니다.
내장 NVMe의 Windows는 그대로 두고, 부팅 디스크를 고르는 것으로 노트북의 역할이 갈립니다.

설치할 때 내장과 외장이 **둘 다 953.87GiB**로 잡혀 용량으로는 구별되지 않습니다.
`/dev/nvme0n1`이 내장이고 `/dev/sda`가 외장 어댑터 칩(ASM2115)이라, 목적지는 이름으로 골라야 합니다.
파일시스템은 ext4로 두어 LVM-thin 풀이 함께 구성되게 했고, ZFS는 단일 USB 디스크에서 쓰지 않았습니다.

## 콘솔에서 서버까지 닿는 길

노트북은 화면을 닫고 두는 서버라, 모든 조작이 데스크탑에서 나갑니다.
그런데 같은 집의 두 기기가 서로 다른 망에 있었습니다.

| 기기 | 주소 | 게이트웨이 | 발급자 |
|---|---|---|---|
| 데스크탑 (유선) | `121.168.x.x` 공인 | 집 **밖** KT 라우터 | KT 직접 |
| 노트북 (WiFi) | `172.30.1.x` 사설 | 거실 공유기 | 거실 공유기 |

데스크탑에서 노트북 쪽 게이트웨이로 보낸 ping이 **100% 손실**이었습니다.
사설 주소는 인터넷에서 배달되지 않으므로, 요청이 집 밖 KT 라우터까지 나갔다가 거기서 폐기됩니다.
노트북이 있는 망의 입구에도 닿지 못합니다.

| 후보 | 판정 |
|---|---|
| 거실 공유기를 방으로 옮긴다 | 가족의 WiFi와 TV가 그 공유기에 물려 있음 |
| 모뎀 빈 포트에 노트북을 직결한다 | 브리지는 호스트 1 + VM 3 = 공인 IP **4개를 새로 요구**. 이미 3개를 쓰고 있어 합계 7개가 되고, 가정 회선에서 성립하지 않음. 받더라도 노드가 NAT 없이 인터넷에 직접 노출 |
| 거실 망에 두고 포트포워딩으로 관리한다 | 웹 UI·SSH·6443이 인터넷 전체에 열리고, 서비스가 늘 때마다 규칙이 누적 |
| 처음부터 방화벽 VM과 VPN으로 간다 | 방화벽은 Proxmox 위의 VM — 관리 통로를 만들 도구를 올리려면 관리 통로가 먼저 필요 |
| 모뎀을 공유기로 대체한다 | KT GiGA UTP는 회선 종단 장비이자 반납 대상이라 대체 불가 |
| **모뎀은 두고 빈 포트에 공유기를 하나 더 단다** | **채택** |

데스크탑이 공인 IP를 반납하고 그 자리를 새 공유기가 받으므로, **집 전체가 쓰는 공인 IP는 3개 그대로**입니다.
옆방과 거실 장비는 건드리지 않아 가족 망에 영향이 없고, 이 공유기가 죽어도 그 아래만 멈춥니다.

**연결은 유선이어야 했습니다.** 브리지에 올라탄 VM은 자기 MAC 주소로 프레임을 내보내야
공유기가 VM을 별개 기기로 등록합니다. 유선 포트는 한 구멍 뒤에 MAC이 여럿인 것이 정상 설계라 이를 받아주지만,
WiFi는 인증을 맺은 MAC 하나와의 연결이라 AP가 낯선 MAC의 프레임을 버립니다. VM 한 대도 통과하지 못합니다.

주소는 자동 발급 구간과 고정 구간을 미리 갈랐습니다.
DHCP 범위를 `.199`까지로 줄이고 `.200` 위를 비워, Proxmox 호스트와 k3s 노드, 로드밸런서 주소 풀이
DHCP와 겹칠 여지를 없앴습니다. 충돌이 난 뒤 대응하는 대신 대역으로 막는 쪽을 택했습니다.

## 노트북을 24시간 서버로

노트북과 외장 USB SSD라는 조건에서 나오는 문제가 셋 있었습니다.

| 조치 | 무엇을 | 그렇게 한 이유 |
|---|---|---|
| 뚜껑 무시 | `logind.conf`의 뚜껑 닫힘 3종을 `ignore` | 서버로 두려면 뚜껑을 닫아야 하는데, 기본값이 그 순간 잠자기 |
| 절전 봉쇄 | `sleep`·`suspend`·`hibernate`·`hybrid-sleep` 타깃을 `mask` | 뚜껑 외에 유휴 타이머나 프로그램 요청으로도 잠들 수 있음 |
| **USB 자동절전 차단** | 커널 파라미터 `usbcore.autosuspend=-1` | 루트 디스크가 외장 USB라, 리눅스가 유휴 USB를 재우면 파일시스템이 끊김 |
| 리포 전환 | 유료 리포를 끄고 무료판 리포를 추가 | 기본이 구독자용이라 업데이트가 401로 막힘 |
| 스왑 성향 | `vm.swappiness`를 60에서 10으로 | 스왑 영역이 외장 USB SSD 위에 있음 |
| 시간 동기 | chrony 동작 확인 | TLS 인증서 검증·노드 간 통신·로그 타임스탬프가 모두 시간에 걸림 |

**적용됐는지는 커널 버전으로 확인했습니다.** 커널은 부팅할 때만 메모리에 올라가므로,
`uname -r`이 `7.0.2-6-pve`에서 `7.0.14-5-pve`로 바뀌었다는 것은 부트로더 설정대로 재부팅됐다는 뜻이고,
같은 부팅에 실린 USB 자동절전 옵션도 함께 발효됐다는 근거가 됩니다.

## 남겨 둔 한계

- **외장 USB SSD가 단일 장애점입니다.** 케이블이 빠지면 서버가 그대로 내려갑니다.
  내장 NVMe의 Windows를 지우지 않으려는 선택의 대가이고, 소프트웨어로 없앨 수 없는 물리 제약입니다.
  대신 자동절전 차단과 종료 절차를 규칙으로 고정해 **끊길 수 있는 경로를 줄이는 쪽**으로 다뤘습니다.
- **벽 배선 구간이 100Mbps입니다.** 랜선 8가닥을 4+4로 갈라 링크 두 개로 쓴 시공이라 이 구간이 상한입니다.
  집 안에서 오가는 트래픽에는 걸리지 않지만, 외부 공개 이후의 상한이 여기서 정해집니다.
